# Hood Up

Hood Up is a dark-mode car workshop booking app for customers and workshop admins. The demo catalog uses Dhaka neighborhoods and BDT prices. Application code is Java, package/application ID is `com.example.carworkshopbookingapp`, minimum Android version is **7.0 / API 24**, and compile/target SDK is **37**.

## Features

- Firebase email/password authentication, role-based entry routing, editable contact profile and owner-scoped cars.
- Cache-first workshop/service browsing, search, Featured/Open now/Top rated filters, dial/maps actions and service selection.
- Hourly booking slots, duration-aware overlap checks, transactional reservation locks, cancellation, status timeline and completed-booking ratings.
- SQLite offline queue and history, bounded foreground sync, live updates while visible and background JobScheduler retries.
- Booking notifications, inexact appointment reminders, connectivity/status broadcasts and reboot reminder rescheduling.
- “Ask the Mechanic”: Gemini structured responses with catalog-only service suggestions, local keyword fallback and persisted chat. Only fixed mechanical concepts and temporary service aliases go to Google; full typed text stays out of the AI request.
- Admin booking management, workshop/service editors, confirmed demo seeding, dashboard totals and a Canvas chart.
- Implemented demo business model: 10% booking commission, featured placement and Hood Up Plus (৳199/month, no real payment). Plus gives 5% off, the first opening-hour slots, a pickup-request flag and earlier reminders. Pickup is a request flag, not a dispatch service.

All navigation uses Activities and Intents. Screens use basic layouts, ListView, Spinner and XML shape styling; there is no Material, RecyclerView, CardView, Compose or fragment navigation architecture.

## Before building or running

A fresh clone needs local configuration and a configured Firebase backend. Prepare the following; `.env`, `app/google-services.json` and `local.properties` are ignored by Git and must be supplied on each developer's machine.

| Item | What to provide | Required for |
| --- | --- | --- |
| `app/google-services.json` | Download the Android app configuration from your Firebase project, registered with package `com.example.carworkshopbookingapp`. Keep the downloaded filename unchanged. | Building and connecting to Firebase |
| Root `.env`: `GEMINI_API_KEY` | Your own Gemini API key with access to the model configured in `ai/GeminiClient.java`. | Live chatbot replies; blank uses local fallback suggestions |
| Root `.env`: `ADMIN_INVITE_CODE` | Leave blank. Gradle still generates this legacy field, but the current app does not read it. | Not required; it cannot provision an admin |
| Root `local.properties` | Your machine's Android SDK path, normally generated by Android Studio. | Locating the SDK for builds |
| Firebase backend | Enable Email/Password authentication, create the default Cloud Firestore database, and publish the repository's rules and indexes. | Registration, sign-in, catalog and bookings |
| Accounts and catalog | Register a customer in the app; have the project owner approve an admin; add services and workshops. | Testing customer/admin flows and making bookings |
| Build tools and device | Android SDK 37, a complete JetBrains JDK 25, and an Android 7.0/API 24 or newer phone/emulator. | Building and running |

### 1. Configure Android Studio and the SDK

Open the project in Android Studio with support for the checked-in Android Gradle plugin. The repository pins Gradle **9.6.0** and AGP **9.5.1**. Install SDK platform **37** and the Build Tools requested by Gradle through SDK Manager.

Use a complete **JetBrains JDK 25**, including `javac` and `jlink`, for the Gradle daemon. `gradle/gradle-daemon-jvm.properties` selects that toolchain. Java source/target compatibility is 11; this does not change the daemon's JDK requirement. Select the matching Gradle JDK in Android Studio. For command-line builds, configure `JAVA_HOME` for your installation and check `./gradlew --version`.

Let Android Studio generate `local.properties` with your SDK location. If creating it manually, set `sdk.dir` to your actual SDK directory. Do not copy another machine's path. No Firebase or Gemini credentials belong in this file.

### 2. Supply `app/google-services.json` and configure Firebase

Use a Firebase project you own or have permission to configure:

1. In the Firebase console, register an **Android app** with package `com.example.carworkshopbookingapp`. Download its `google-services.json` into the repository's `app/` directory. Use the configuration from the same project in which you will create accounts and publish rules.
2. Enable **Authentication → Sign-in method → Email/Password**.
3. Create the **default Cloud Firestore database**. Publish root `firestore.rules` through **Firestore Database → Rules**, and create the composite indexes described in `firestore.indexes.json`. Wait for indexes to finish building.
4. Alternatively, with Firebase CLI installed and signed in to an account authorized for the intended project, deploy both checked-in files from the project root. Replace the placeholder with your Firebase project ID:

   ```sh
   firebase login
   firebase deploy --only firestore:rules,firestore:indexes --project YOUR_FIREBASE_PROJECT_ID
   ```

Building or installing an APK does not publish rules, create indexes, enable authentication or populate Firestore. The app connects to the Firebase project in `google-services.json`; it does not automatically connect to the local emulator configured in `firebase.json`.

The current Android app uses Firebase Authentication and Firestore. You do not need a Firebase service-account JSON/private key, a Cloud Storage bucket, a payment credential or a Maps API key to run it. Maps and phone actions open external apps.

### 3. Create the root `.env`

Create `.env` beside `gradlew`, using exactly these variable names. These empty values are placeholders:

```dotenv
GEMINI_API_KEY=
ADMIN_INVITE_CODE=
```

- **`GEMINI_API_KEY`**: obtain your own key from Google AI Studio. The current client requests `gemini-3.5-flash-lite`; ensure the key's project has API/model access and available quota. Without a usable key, the chatbot reports the problem and uses local suggestions. A working online Gemini response is required to demonstrate the live AI integration.
- **`ADMIN_INVITE_CODE`**: leave empty. This is a legacy build field, unused by the current application. Admin access is granted through the Firestore role procedure below.

The Gradle script reads this root file at **build time**, supports quoted values, and generates the corresponding `BuildConfig` fields. Missing values become empty strings. Exporting shell variables alone does not configure these fields. After changing `.env`, rebuild and reinstall the APK; editing the file does not update an installed app.

Keep actual credentials out of source, screenshots and commits. BuildConfig values are extractable from an APK. Configure API restrictions and quotas for your key; the client sends the app package and signing-certificate SHA-1 headers. If Android application restrictions are used, allow the certificate that signs the APK being tested. A production deployment should move the Gemini key behind an authenticated backend.

### 4. Build, install and prepare accounts/data

1. With the files and Firebase setup above complete, build and install:

   ```sh
   ./gradlew assembleDebug
   adb devices
   adb install -r app/build/outputs/apk/debug/app-debug.apk
   ```

   Enable USB debugging and authorize the computer for a physical device, or start an emulator. Android Studio's Run action can also build and install the app.

2. Start online and register a customer with a name, phone number, email and password. This creates both the Firebase Auth account and its matching `users/{uid}` profile. Creating only an Authentication account in the console is insufficient for app sign-in.
3. To provision an admin, first register that person through the app. The trusted project owner must verify the account's UID and change **only** its existing `users/{uid}.role` field to the string `admin` in Firestore. Preserve all other profile fields. Log out and use **Admin login** with that account's email/password. Customer clients cannot promote themselves.
4. In the admin dashboard, open **Services → Add service**. Supply a name, category, description, BDT base price, duration (1–300 minutes), and relevant symptom keywords. Prices support at most two decimal places.
5. Open **Workshops → Add workshop**. Supply a name, area, description, address, phone number, opening/closing hours and image choice, then choose at least one saved service. Use whole-hour times; equal opening and closing hours mean 24-hour operation. The current app has no demo seed button: a new Firebase project starts with an empty catalog.
6. Log in as a customer, add a car under **My Cars**, and choose a workshop/service to make a booking. Catalog entries and offered-service links are needed for booking and useful chatbot recommendations. Booking times use **Asia/Dhaka** and prices use **BDT**.
7. On Android 13 or newer, allow notification permission when prompted to test booking notifications and reminders. No location permission or Maps SDK setup is needed for the external maps action.

SQLite tables and caches are created automatically; no local database file or SQL import is required. Initial authentication and catalog loading require internet access. Offline features use data cached on that installation.

### First-run verification

On a phone or emulator, register/sign in, confirm the configured catalog appears, add a car and submit a test booking. With the approved admin, confirm the booking is visible and update its status; return to the customer and check the update. Open **Ask the Mechanic**, send a symptom such as “My AC blows warm air,” and verify an online reply and a catalog service suggestion; a fallback reply alone does not verify the Gemini key. Allow notifications and confirm a booking notification, then disconnect networking and reopen previously cached listings.

These are device checks for the person setting up the app; documenting them does not mean they have been executed against that person's Firebase project or API key.

## Architecture

```text
               Plain Activities + explicit Intents
                ui/ and ui/adapter/ (ListView)
                              |
                callbacks posted to main Handler
                              |
       +----------------------+-----------------------+
       |                      |                       |
 data/ stores           ai/ ChatSession          service/ SyncCoordinator
 BookingStore           GeminiProtocol          BookingSyncService (started)
 CarStore               FallbackAdvisor         BookingSyncJob
 BookingSubmission      GeminiClient                  |
       |                      |                       |
       +---------- util/ AppExecutors ----------------+
       |              IO / network pools              |
       v                      v                       v
 data/local/            HTTPS Gemini REST        data/remote/
 LocalDb (SQLite)       (concepts + aliases)      Firestore repositories
 SessionStore                                      + Firebase Auth
       ^                                              |
       +---------- cache, queue and snapshots ---------+
                              |
             receiver/ connectivity/status/boot/alarm
                              |
             NotificationHelper + ReminderScheduler
```

SQLite work and Firestore request/mapping work run off the main thread. Gemini's blocking HttpURLConnection uses a separate network executor. Live subscriptions and UI observers are closed/detached with their lifecycle. Rotation stays enabled; form drafts use saved state and chat/queue data use SQLite.

## Tests and API 24 compatibility

```sh
./gradlew test
./gradlew assembleDebug assembleRelease lint
./gradlew assembleDebugAndroidTest
```

JUnit tests in `app/src/test/java/` cover commission/discount rounding and invalid money, every status transition, fallback keyword ranking and matching, Gemini response/envelope parsing and malformed JSON, request privacy/alias mapping, duration-aware slots/locks/closed days, rating aggregates and reminder policy. JSON contract tests use a **test-only** org.json dependency; the Android app uses platform org.json. `test` runs the configured JVM suite (currently `testDebugUnitTest`); the release APK is built separately. HTML reports land under `app/build/reports/tests/`.

For local Firestore authorization tests, `cd security-tests`, run `npm ci` then `npm test` (Node/npm and Java 21+ required). The fixed `demo-hood-up` emulator project does not deploy to production.

`minSdk` stays 24 in both variants. Lint's API checks must remain enabled: channel/foreground APIs, signing certificates, notification permission and animation helpers are guarded with SDK checks; Java collection/default methods used by the app are available at API 24. API 24 also has native vectors, NetworkCallback and the selected alarm APIs. APK signature verification with a minimum SDK of 24 verifies signing compatibility, not application runtime behavior.

An actual Android 7.0/API 24 phone or emulator is still needed to verify installation, rendering, Firebase connectivity and full runtime behavior. Building and lint passing cannot substitute for that device check. Follow the [phone QA table](docs/MANUAL_QA.md) and [release instructions](docs/RELEASE.md).

## APKs and installation

See [RELEASE.md](docs/RELEASE.md) for exact build/signing commands and ownership of signing keys.

| Artifact | Path | Signing / purpose |
| --- | --- | --- |
| Debug | `app/build/outputs/apk/debug/app-debug.apk` | Automatically signed with the local Android debug key |
| Release build | `app/build/outputs/apk/release/app-release-unsigned.apk` | Release variant; not installable until signed |
| Demo release | `app/build/outputs/apk/release/app-release-demo.apk` | Release variant signed with the local debug certificate; for direct demo installation only |
| Owner-signed release | Chosen output, e.g. `app/build/outputs/apk/release/app-release.apk` | Signed using the owner's release key via Android Studio or apksigner |

Enable USB debugging, authorize the computer, then:

```sh
adb devices
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

Or transfer a **signed** APK to the phone, open it in Files and temporarily allow that source to install apps. A signing-certificate mismatch prevents in-place updates: use the same key, or uninstall only after preserving needed data (uninstall deletes local data).
